Paperclip para equipos de desarrollo: roadmap de 0 a 100

Paperclip es un control plane open source (MIT) que organiza los agentes que ya usas (Claude Code, Codex, Cursor, Gemini CLI, OpenClaw) en un organigrama con metas, tareas, heartbeats, presupuestos con parada automática y aprobaciones humanas. Esta página resume la investigación completa que vive en el repo paperclip-roadmap (9 documentos + plantillas).

Qué es y qué no es

Los 7 conceptos

Company
org aislada con meta, agentes, tablero y presupuesto
Agente
rol + un solo jefe + budget mensual + adapter (runtime real)
CEO
primer agente; propone estrategia, tú apruebas (default: 20 palabras, escribe el tuyo)
Goals
Misión → meta de proyecto → meta de agente → tarea
Issues
backlog→todo→in_progress→in_review→done, checkout atómico
Heartbeat
ventana de ejecución: timer, asignación, comentario, aprobación, rutina (la mención @ ya no despierta)
Budgets
aviso 80 %, pausa 100 %, por empresa/agente/proyecto; actúa entre runs

Qué NO es (según sus docs)

  • No es un chatbot ni una herramienta de un solo agente ("si tienes un agente, no necesitas Paperclip").
  • No es code review: "trae tu propio proceso". Los agentes nunca hacen merge.
  • No corre modelos: bring your own agent, tú pagas a Anthropic/OpenAI.
  • No bloquea el shell ni los archivos del runtime; desde 1001.0 corre en full auto por defecto. Restringe explícitamente a los agentes expuestos a input hostil.
  • No sincroniza Jira/Linear bidireccionalmente (roadmap). Hoy Jira es acceso MCP para leer/comentar/transicionar.
  • Slack: reconstruido en octubre (chat bidireccional, herramientas para agentes), pero sigue experimental y marcado "no completamente funcional".

Roadmap en 7 fases

Las fases 0–2 son comunes a los tres escenarios. Cada fase tiene un criterio de salida medible. Comandos completos en docs/03-roadmap-0-a-100.md.

FASE 0 · 2–3 días

Decidir

Repo piloto de bajo riesgo, 10 issues "agent-ready", cuentas y presupuesto
  • CI + branch protection + AGENTS.md en el repo piloto
  • Inventario: Claude Max/Codex + API keys de respaldo
  • Tope del experimento: US$100–300 el primer mes
Done: doc de una página con repo, issues, presupuesto y responsable humano
FASE 1 · 1 semana

Laboratorio

npx paperclipai test-drive → org → CEO → plantilla → repo
  • Importar gstack o superpowers desde paperclipai/companies; escribir el AGENTS.md del CEO (el default son 20 palabras)
  • Org construida con todo pausado; activar de uno en uno, sin timers
  • Workspaces aislados (flag experimental) + maxConcurrentRuns: 1
  • PAT fine-grained como secret, skill github-pr-workflow
Done: 3 PRs fusionados por ti, costo por PR conocido
FASE 2 · 2–4 días

VPS + Docker

4 vCPU / 8 GB, Postgres 17 externo, Caddy TLS, modo authenticated
  • En Proxmox: VM Ubuntu 24.04 (no LXC), 4 vCPU, 12–16 GB
  • docker build --target production (obligatorio); versión ≥ 2026.1012.0
  • Backups + master.key fuera del servidor; strict mode; API key de respaldo para suscripciones
Done: 2+ personas con login, heartbeat en servidor, backup restaurado
FASE 3 · 1 semana

Primer repo real

CTO + Coder + QA; review agente + aprobación humana en cada issue
  • Coders sin timer (on-demand); CTO 1–2 h en horario laboral
  • Budgets: company 300 · CTO 40 · coder 25 · QA 15 USD
  • Métricas diarias: PRs, rondas, costo/PR, minutos humanos
Done: ≥10 PRs fusionados, rechazo <30 %, post-mortem escrito
FASE 4 · 1–2 semanas

Equipo completo

Añadir roles sólo donde hubo cuello de botella
  • Backend (Codex), Frontend (Claude), QA, Reviewer de otra familia, Docs/Release (mini)
  • Rutinas: triage diario, daily brief 07:00, sync semanal
  • Skills propias del stack; watchdogs en épicas
Done: un sprint de issues S/M cerrado sólo con revisión y aprobaciones
FASE 5 · 1 semana

GitHub + Jira + Slack

GitHub App, agente-espejo de Jira, Slack nativo + notificador
  • GitHub App; Code Review Bot como check "Paperclip Review" con umbral numérico
  • Jira: rutina lee sprint activo, crea issues espejo; escrituras "ask first"
  • Slack nativo (Chat connectors + HTTPS público, wizard de 7 pasos) + notificador de aprobaciones/bloqueos
Done: aprobaciones y bloqueos en Slack en <2 min; cada issue con clave Jira
FASE 6 · continuo

Operación y escala

Ritual semanal de costos, una org por cliente, runner separado
  • paperclipai update con backup automático; 1012.0 exige drenar procesos
  • Assistant Connection: cada dev opera Paperclip desde Claude Code
  • OTel/Sentry; kill switch = pausar empresa + hard stops; memoria experimental sólo si hace falta
Done (el 100): ≥30–50 % de issues S/M cerrados por agentes cada sprint, costo/PR estable, cero incidentes

Riesgo

Presupuesto

Casos de uso reales

Evidencia de uso: 14,267 commits públicos atribuidos a Paperclip en 884 repos (estudio oficial, marzo 2026), pero la mediana es de 3 commits por repo. Perfil dominante: founders técnicos con TypeScript/Next.js. Entre septiembre y octubre no apareció ningún caso de equipo de software con PRs/día o costo por feature publicados.

1 · PR nocturno

Issue → worktree → branch → commit → PR → QA agent → aprobación humana → merge. Flujo canónico documentado y usado por el propio equipo de Paperclip.
Medir: PRs/día, % fusionados sin cambios, costo por PR

2 · Deuda técnica y migraciones

Una meta con métrica → CTO agent la parte en 45 sub-issues S → 2 coders en paralelo → watchdog en la épica. Skill de empresa con el mapeo "antes/después".
Medir: sub-issues/día, regresiones en CI

3 · QA agent como puerta

Skill qa-acceptance, criterios Given/When/Then, screenshots. maxReviewRounds: 3 escala al humano si no converge.
Medir: bugs atrapados antes del review humano

4 · Triage de bugs fuera de horario

Rutina 22:00 lee Jira (MCP) filtrando agent-ready, reproduce, escribe el test que falla y abre PR con fix propuesto. Sentry → webhook → issue.
Medir: tiempo a primera respuesta, % fixes aceptados

5 · Docs y releases

Webhook pull_request.closed → issue "actualiza docs"; rutina semanal → changelog + release notes → aprobación.
Medir: docs desactualizados en retro

6 · Onboarding a repo desconocido

Primer issue: "explora y escribe ARCHITECTURE.md + comandos + riesgos" → se vuelve skill de la org del cliente.
Medir: horas humanas ahorradas

7 · Daily brief

Rutina 07:00 → status card → Slack: cerrado, bloqueado, aprobaciones pendientes, gasto del mes.
Reemplaza el standup del trabajo de agentes

8 · Segunda revisión de PRs

GitHub Code Review Bot (1005.0): puntaje 1–5, hallazgos inline, check "Paperclip Review" exigible en un ruleset. Segunda opinión, el merge sigue siendo humano.
Medir: hallazgos reales vs falsos positivos

9 · Slack como bandeja

Mención en un hilo = tarea; las respuestas del board vuelven al hilo. Sólo miembros vinculados ordenan trabajo.
Medir: tareas creadas desde Slack, tiempo de respuesta

10 · QA visual

Browser Use Cloud o skill agent-browser: el QA recorre la preview en un navegador visible desde la tarea, con takeover humano.
Medir: bugs visuales antes del merge

11 · Operar desde Claude Code

Assistant Connection (MCP, experimental): claude mcp add --transport http paperclip … y cada dev crea, consulta y comenta tareas sin abrir la UI.
Conecta como la persona, no como un agente

12 · Auditoría de seguridad

Plantilla oficial Trail of Bits recortada a 3–5 agentes, repo en lectura, preset low_trust_review + sandbox, rutina mensual.
Medir: hallazgos confirmados por un humano

13 · Mantenimiento OSS "inbox zero"

Plantilla comunitaria micronaut-agent-company: 9 roles, GitHub sync, Renovate, workspaces aislados.
Medir: issues sin respuesta > 48 h

14 · DevOps/IaC por tickets

Equipo sobre Proxmox (Terraform + Ansible + Tailscale): router en Haiku, SRE/Platform/Security en Sonnet, kubectl en lectura hasta aprobar un "access task", cero timers.
Patrón "router delgado", no "CEO que piensa"

15 · Noche en tres carriles

Guía oficial del 12 oct: avanza y se detiene (refactors, tests, PRs draft) · prepara y decide un humano (merges, releases, migraciones) · espera (lo ambiguo). Cada límite en la capa que lo aplica.
Checklist matutino: blocked, in_review, costos, activity log

Recomendación A

Claude Code + Codex para trabajo interactivo; GitHub Agent HQ para "issue → PR" sin infra; Paperclip self-hosted como runner 24/7 del backlog agent-ready, guardián de gasto y auditoría. Si en 3 meses sólo usas "issue → PR", baja a Agent HQ.

Recomendación B

Paperclip es la mejor de su categoría para un solo founder: CEO → equipo, presupuestos y aprobaciones sobre suscripciones Max/Pro, 3–4 agentes, CEO una vez al día.

Recomendación C

Una org por cliente para quienes acepten self-hosting. Para clientes con SOC2/SSO: Copilot Enterprise + Agent HQ, Devin/Factory, Rovo Dev; Paperclip sólo interno tras Tailscale.

Los 10 mandamientos

  1. Versión ≥ 2026.1012.0, modo authenticated, UI tras Tailscale o TLS, puerto 3100 cerrado. Full auto es el default: restringe a los agentes que leen input hostil.
  2. Postgres 17 externo, backup diario y secrets/master.key fuera del servidor.
  3. Empieza con 3–4 agentes desde superpowers o gstack; añade sólo donde aparezca un cuello de botella.
  4. AGENTS.md tipo "job posting" (deberes, autoridad, límites, qué NO hace) con regla anti-fabricación y reglas PR-driven.
  5. Workspaces aislados y maxConcurrentRuns: 1 antes del segundo agente ingeniero.
  6. Presupuesto con hardStopEnabled en empresa y agentes el día 1, más límites en las consolas del proveedor (el tope actúa entre runs) y API key de respaldo para suscripciones (expiran a las ~8 h, bug abierto).
  7. Timers sólo en managers y en horario laboral; ingenieros sólo on-demand. Construye la org con todo pausado y activa de uno en uno.
  8. Review por agente de otra familia de modelos + aprobación humana; merge sólo por humanos con branch protection.
  9. Issues agent-ready ≤ 400 líneas con criterios observables y condición de parada.
  10. Mide desde el día 1: PRs fusionados, rondas de review, minutos humanos por PR, costo por PR. Nadie ha publicado estos números.
